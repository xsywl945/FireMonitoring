# 系统设计说明

本文描述当前 main 中的程序，不描述 `docs/plans/` 里已经放弃的 Java、Redis 或独立推理进程。那些目录保留为当时的记录。

界面和 FastAPI 标题是「火情监控」。`pyproject` 中的包版本是 1.0.0。申报和软著材料另拟名称「校园智能火情预警与辅助决策系统 V2.0」，那个名称还没有写进程序版本号。

## 1. 架构

一个 FastAPI 进程负责账号、教室、摄像头、检测调度、告警、证据、短信、灭火状态机和串口。前端是 Vue 3、TypeScript、Vite 和 Element Plus。时序、几何、规则、千问客户端、灭火状态机和两套串口协议在 `apps/inference`，由后端在同一进程中调用。

```text
USB 摄像头 -> FFmpeg -> MediaMTX -> 浏览器 WHEP
网络摄像头 RTSP --------^              |
                         RTSP          |
                           v           |
                        检测线程 -> 时序确认 -> 告警
                           |              |
                           v              v
                     两到四路定位      灭火状态机
                           |              |
                         MySQL        执行节点 / 报警节点
                         MinIO
                         千问、短信（可关闭）
```

演示模式不走这条实况链路。它读 `data/demo/synthetic-classroom`，用包内图像和检测框回放，硬件默认用进程内的模拟设备。

设置环境变量 `FIRE_WEB_DIST` 后，后端用 `apps/web/dist` 提供页面，并把未知路径回退到 `index.html`。`/api` 仍由原来的路由处理。不设置该变量时，页面由 Vite 单独提供。

## 2. 模块

| 路径 | 职责 |
|---|---|
| `apps/server/src/fire_monitoring/main.py` | 组装配置、数据库、对象存储、检测线程、灭火和演示 |
| `auth` | 口令哈希、JWT、管理员依赖。角色只接受 `admin` 和 `operator` |
| `rooms`、`cameras` | 教室、绑定、摄像头和标定的 HTTP 接口。教室最多 4 个槽位 |
| `calibration` | ChArUco 内参、控制点外参、标定板 PDF、画面清晰度 |
| `detection` | RTSP 采集、环形缓冲、批量检测、健康检查。检测线程抛错则进程退出 |
| `alerts` | 确认后的定位、关键帧、片段、研判、短信、处置和导出 |
| `analysis` | 调用千问适配器，提示词版本 `fire-evidence-v4`。模型不选择灭火剂 |
| `localization` | 把检测框变成观测。火用框底边中点，烟用框中心 |
| `suppression` | 按房间推进状态机，向泵和报警节点发效果 |
| `pump` | `FIRE_ACTUATOR_V2` 的主机侧发送和 SQLite 记录 |
| `sms` | 阿里云模板短信。同一教室有冷却时间 |
| `streams` | 按摄像头表生成 MediaMTX 配置 |
| `demo` | 合成包、剧本播放、模拟或真实串口 |
| `apps/inference` | 时序、多视几何、规则、弹道、状态机、两套固件协议的主机实现 |
| `firmware/esp32_actuator` | 执行节点固件 |
| `firmware/esp32_panel` | 报警节点固件 |
| `apps/web` | 页面。契约类型在 `src/api/types.ts` |
| `config/fire_rules.json` | 场景先验和灭火剂规则 |
| `ml` | 数据集和训练脚本。在线进程不调用它 |

检测从 MediaMTX 的 RTSP 读流，不直接打开摄像头。每路采集只保留最新帧，并按 2 fps 保留约 15 秒。告警后保存事件前 5 秒和后 10 秒的 mp4。检测频率不超过该路 `target_fps`。确认之后才做定位、千问、短信和灭火，这几步不在检测线程里阻塞画面读取。从确认到 WebSocket 发出的毫秒数记在日志 `fire_monitoring.alerts`。

对象存储使用 MinIO。桶不存在时后端创建。演示和测试可以换成内存实现，正式启动不会自动换成内存。

## 3. 协议

HTTP 契约以运行中的 `http://127.0.0.1:8080/openapi.json` 为准。浏览器通过 `/api/v1/events` 的 WebSocket 接收事件，查询参数携带登录令牌。

执行节点串口协议 `FIRE_ACTUATOR_V2`，115200 8N1，一行一条，以 LF 结束。主机命令包括 `HELLO`、`PING`、`STATUS`、`RUN`、`STOP`、`AIM`、`LASER` 和 `UNLOCK`。`RUN` 的时长为 100 到 30000 毫秒。水平瞄准为 -12000 到 12000 百分度，俯仰为 0 到 6000 百分度，实际转动不超过 90°/s。泵或激光开启时，3000 毫秒没有主机命令就关闭输出。GPIO 不证明出了水。没有收到明确的 `ACK <id> ON` 之前，主机不把这次 `RUN` 当成成功，也不用同一个 id 再发一次。细节见 `contracts/actuator-serial-v2.md`。

报警节点协议 `FIRE_PANEL_V2`，同样 115200 8N1。模式为 `OFF`、`GREEN`、`YELLOW`、`RED_BLINK`、`RED_SOLID` 和 `ALT`。灯光闪烁由固件按 2 Hz 产生。静音键只关蜂鸣。3000 毫秒没有主机命令时，固件自行改为 `ALT`，并上报链路 `DOWN`。细节见 `contracts/panel-serial-v2.md`。

短信使用阿里云模板。变量是 `location`、`level` 和 `method`，各不超过 35 个字符。模板草稿见 `docs/sms/aliyun-template-v2.md`。

## 4. 数据表

表在后端启动时由 SQLAlchemy 创建。时间字段带时区。

| 表 | 字段 |
|---|---|
| `users` | `id`，`username`，`display_name`，`password_hash`，`role`，`created_at` |
| `rooms` | `id`，`name`，`scene_type`，`floor_plan_json`，`created_at` |
| `cameras` | `id`，`name`，`source_type`，`source_uri`，`stream_key`，`target_fps`，`calibration_json`，`created_at` |
| `room_cameras` | `id`，`room_id`，`camera_id`，`slot`。同一教室的摄像头、同一教室的槽位分别唯一 |
| `alerts` | `id`，`room_id`，`alert_type`，`started_at`，`position_json`，`analysis_json`，`observations_json`，`status`，`level`，`fire_classes` |
| `alert_frames` | `id`，`alert_id`，`camera_id`，`object_key`，`captured_at`。同一告警的同一摄像头唯一 |
| `alert_clips` | `id`，`alert_id`，`camera_id`，`object_key`，`started_at`，`ended_at` |
| `alert_dispositions` | `id`，`alert_id`，`action`，`note`，`actor`，`occurred_at` |
| `alert_events` | `id`，`room_id`，`alert_id`，`kind`，`detail_json`，`occurred_at` |
| `device_events` | `id`，`camera_id`，`kind`，`occurred_at` |
| `sms_dispatches` | `id`，`room_id`，`sent_at` |

告警状态是 `OPEN`、`ACKNOWLEDGED`、`FALSE_ALARM`、`CLOSED`。类型是 `FIRE`、`SMOKE`、`FIRE_AND_SMOKE`。

水泵命令记录不在 MySQL，而在 `pump.journal_path` 指向的 SQLite。云台拟合结果在 `suppression.gimbal_path`，默认 `runtime/gimbal.json`。这两个文件都在本机运行目录，不提交。

平面图、关键帧和片段的对象键存在表里，文件在 MinIO 桶中，默认桶名 `fire-evidence`。

## 5. 状态机

### 时序确认

每一路、每一个类别（火或烟）单独累计。样本窗口长度是 `temporal.m`。窗口内达到阈值的次数大于等于 `candidate_n` 时，从正常进入疑似；大于等于 `n` 时进入已确认。要求 `candidate_n <= n <= m`。连续 `clear_frames` 帧没有目标时，已确认进入冷却，疑似回到正常。冷却时长是 `cooldown_ms`。冷却结束回到正常。正常和冷却不向外提供证据。

检测器先用两个类别阈值中较低的一个做初始过滤，再按类别丢掉不够的框。低于类别阈值的框不进入这个状态机。

### 灭火

每个教室一台状态机。输入包括本地是否确认火焰、是否有烟、研判、定位、人员、心跳、急停、证据年龄和云台参数。

- 监视：本地确认火焰或手动喷水则进入已确认；只有烟则进入疑似。
- 疑似：出现火焰进入已确认；烟消失回到监视。
- 已确认和瞄准：联锁不通过就留在已确认，并记下原因。通过则瞄准，然后进入待喷。
- 待喷：经过 `pending_seconds` 后进入喷射，并请求 `RUN`。
- 喷射：经过喷水时长后进入复核。
- 复核：连续 `clear_seconds` 没有火焰则已扑灭。火焰面积没有明显下降、且修正次数达到 `max_corrections` 时，进入需人工处置并停止。否则按落点或协方差修正，回到瞄准。
- 锁定：网页急停，或固件锁为 `LATCHED`、`ARMED`。进入锁定时停止输出。管理员解锁要求网页急停已经松开，且固件不再是 `LATCHED`。

联锁在 `spray_block` 中按固定顺序拒绝：摄像头停止、证据过期、泵未启用、教室不在覆盖范围、本地火焰未确认、规则禁水、要求千问但未确认、未定位、协方差过大、无法瞄准、附近有人、心跳中断、冷却未到、覆盖概率不足。覆盖不足且还没有扫射路径时，把定位协方差投到落点平面，沿主轴铺 2σ 椭圆。落点个数上限是 `max_water_s` 除以单次喷射时长。路径放得进这个上限，并且名义覆盖概率不低于 `cover_threshold`，才改走扫射并重新判断；否则留在已确认，不喷水。

规则类别是 A、B、C、D、E、F。证据和场景先验由 `config/fire_rules.json` 决定。模型返回的字段若不符合模式，研判记为失败，不自行选择灭火剂。

### 演示播放

演示播放器按合成包的帧率推进剧本时钟，把包内 JPEG 和检测框送进同一套时序、定位和灭火代码。速度为 0 时不按帧率睡眠，只受计算速度限制。包要求待喷 3 秒、喷射 5 秒、清除 3 秒，与当前配置不一致就拒绝播放。

## 6. 部署边界

实况路径依赖 Docker 中的 MySQL 和 MinIO、本机的 MediaMTX 和 FFmpeg，以及可选的两块 ESP32。演示路径依赖 MySQL 和 MinIO，不依赖摄像头、MediaMTX 和串口。

权重、`config.json`、`.env` 和运行时数据库都不进入 Git。日志不应当打印密钥；配置接口返回前会去掉密钥。文档和脚本同样不写入密钥。
